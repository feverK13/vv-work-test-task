## VV Work — тестове завдання

MVP job-платформи VV Work: 3 сторінки (Головна, Сторінка партнера, Контакти),
Vite + React + TypeScript + Tailwind CSS. Без UI-кітів (shadcn/Radix/MUI),
без Redux/Zustand — стейт живе локально в компонентах, що його використовують.

## Інструкція запуску

```bash
git clone <repo-url>
cd vv-work-test-task
npm install
npm run dev        # http://localhost:5173
npm run build      # production build
npm run preview    # preview production build
npm run test       # unit tests (Vitest + Testing Library)
npm run lint       # ESLint
```

## Стек

- Vite, React 18, TypeScript (`strict: true`, жодного `any` в коді)
- Tailwind CSS v4
- React Router v7
- Vitest + @testing-library/react + @testing-library/user-event
- Lucide React для іконок

Без UI-кітів, без Redux/Zustand — так вимагає бриф.

## Архітектура

- `src/api/` — mock API wrapper (`mockFetch`: випадкова затримка 300–800мс,
  10% шанс помилки) та функції поверх нього під конкретні сутності
  (`fetchPartners`, `fetchPartnerBySlug`, `fetchVacanciesByPartner`,
  `submitApplication`)
- `src/hooks/` — перевикористовувані хуки (`useDebounce`,
  `useVacancyFilters`, `useFormValidation`, `useScrollReveal`,
  `useActiveSection`, `useGridColumnCount`)
- `src/components/ui/` — примітиви дизайн-системи (`Button`, `Input`,
  `Badge`, `Skeleton`, `RetryBlock`, `ApplicationForm`, `SectionLabel`)
- `src/components/layout/` — `Header`, `Footer`, `Layout` (React Router
  Outlet-патерн: спільні хедер/футер обгортають усі сторінки через один layout)
- `src/pages/` — компоненти сторінок (`home/`, `partner/`, `contacts/`,
  `not-found/`)
- `src/types/` — доменні типи (`Vacancy`, `Partner`, `Category`) в одному місці
- `src/utils/` — чисті функції валідації
- `src/data/` — mock-дані (партнери, вакансії, категорії)

Сторінка партнера завантажує інфо про партнера й список вакансій двома
незалежними `useEffect`, а не `Promise.all` — щоб retry одного запиту не
чіпав інший і не дублював час очікування там, де це не потрібно.

## Мої рішення

Бриф дає тільки 3 сторінки, але `/partners/:slug` — динамічний роут, і звідкись треба брати slug. Окремої сторінки "всі партнери" в скоупі нема. Тому на Home зробив блок "Партнери" з картками, кожна веде на свою `/partners/:slug`. Клік по категорії веде на першого партнера зі списку, з `?category=` як початковим фільтром. Так у користувача завжди є шлях до вакансій, без глухих кутів.

Бриф забороняє Redux/Zustand, а стану в застосунку вистачає: асинхронні дані, пошук з фільтром, форма, UI-перемикачі. Не став нічого городити — кожен асинхронний компонент сам тримає свій loading/error/data через `useState`+`useEffect`. Пошук і фільтр об'єднав через `useMemo` з AND-логікою. Стан форми виніс в окремий хук `useFormValidation`. Для 3 сторінок так простіше й легше підтримувати, ніж тягнути глобальний стор, і кожен стан лежить поруч з компонентом, який його використовує.

Бриф окремо оцінює, чи немає зайвих ре-рендерів у списку вакансій. Обгорнув `VacancyCard` в `React.memo`. `useVacancyFilters` повертає результат `Array.filter()` — ті самі референси об'єктів, тому memo не ламається. Через це набір тексту в пошук не ре-рендерить картки, які й так лишаються на екрані. Це не просто теза: є тест, який рендерить 3 картки, вводить запит, чекає дебаунс і перевіряє — картка, яка лишилась видимою, відрендерилась рівно 1 раз, не 2 (`src/pages/partner/vacancy-list.test.tsx`).

Частоту помилок mock API зменшив з 20% до 10%. Бриф каже ~1 з 5, але на сторінці партнера два паралельні запити, і шанс побачити хоч одну помилку — 36%. Перше враження від сайту було б "щось зламане". З 10% retry і skeleton все ще легко побачити при повторних заходах, а перший візит майже завжди проходить нормально. Тут UX важливіший за буквальне виконання специфікації — логіка retry повністю робоча і покрита тестами, я просто зробив помилки рідшими, а не приховав їх.

Бриф просить форму "inline під карткою", але якщо вставити її прямо в grid-елемент, вона розтягує сусідні картки в тому ж рядку. Тому форма рендериться окремим `col-span-full` елементом під усім рядком грида, а не всередині картки. Відкрита завжди тільки одна — відкриваєш іншу, попередня закривається. Позицію рахую динамічно за фактичною кількістю колонок (`ResizeObserver` через `useGridColumnCount`), щоб розкладка не ламалась на жодному брейкпоінті.

## Відхилення від брифу

Прибрав "Про нас" з навігації — такої сторінки чи секції немає в скоупі 3 сторінок. "Знайти працівника" перейменував на "Для роботодавців" — так зрозуміліше, кому цей пункт меню. Помилка поля форми зникає одразу при зміні значення, а не тільки на blur, щоб застаріле повідомлення не висіло, поки людина вже виправляє ввід. Частоту помилок mock API знизив з 20% до 10% (деталі — в "Мої рішення" вище). Додав дещо поза скоупом брифу: 404-сторінку, favicon, кнопку "нагору", кнопку "Скинути фільтри" коли фільтр нічого не знайшов, кастомний скролбар, декоративні елементи.

## Unit-тести

30 тестів, що покривають три області, які вимагає бриф:

- **Дебаунс пошуку**: поведінка таймера хука, очищення при анмаунті,
  скасування при швидкому вводі — окремі ізольовані тести хука
  (`src/hooks/use-debounce.test.ts`). Інтеграційно — кількість
  ре-рендерів відфільтрованого списку (`src/pages/partner/vacancy-list.test.tsx`).
- **Валідація форми**: мінімальна довжина імені, формат телефону/telegram,
  максимальна довжина повідомлення, очищення помилки при зміні,
  повторна валідація на blur (`src/utils/validators.test.ts`,
  `src/components/ui/application-form.test.tsx`).
- **Оптимістичний UI + retry**: стан "успіх" ще до відповіді запиту,
  захист від подвійного сабміту, повторна спроба після фонової помилки
  зберігає дані форми (`src/components/ui/application-form.test.tsx`);
  на рівні самої mock-обгортки — resolve/reject за випадковістю і
  затримка в діапазоні 300–800мс (`src/api/mock-fetch.test.ts`).
- **Розміщення форми в гриді**: форма рендериться поза карткою, лише
  одна форма відкрита одночасно (`src/pages/partner/vacancy-list-expand.test.tsx`).

Запуск: `npm run test` / `npm run test:coverage`

## Доступність

- Семантичний HTML (`nav`, `main`, `article`, `section`, `footer`)
- Focus-visible рамки на всіх інтерактивних елементах
- `prefers-reduced-motion`: усі анімації вимикаються

- `sr-only`-лейбли на полі пошуку
- `touch-action: manipulation` для швидкого відгуку на дотик на мобільних
